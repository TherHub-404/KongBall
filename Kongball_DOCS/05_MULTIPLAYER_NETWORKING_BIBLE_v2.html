Gameplay Engineering Bible · KB 05

Multiplayer & Networking

A network architecture for a fast, chaotic third-person football game where movement, collisions and the ball must remain responsive while the server remains authoritative.

Design target: Local control should feel immediate; shared reality should remain consistent and cheat-resistant.

CORE PRINCIPLE
Predict locally, validate authoritatively. The client can predict what the player intends to do, but the client cannot decide the shared reality of the match.

01 — The Fundamental Problem

Our game has exactly the systems that make networking difficult:

  • Fast third-person movement.
  • Player-player collisions.
  • Knockback and ragdoll.
  • A highly interactive ball.
  • Short action windows.
  • Many simultaneous players.

Networking must therefore be considered part of gameplay architecture, not an integration task at the end.

03 — What the Client Owns

The client owns input and presentation, not truth.

  • Local input.
  • Local predicted movement.
  • Camera.
  • Animation presentation.
  • Local VFX/SFX.

04 — What the Server Owns

  • Match state.
  • Player authoritative state.
  • Ball authoritative state.
  • Goals.
  • Score.
  • Critical interactions.
  • Validation.

06 — Reconciliation

When the server disagrees with the client, correct the client without producing visible teleportation whenever possible.

  • Store recent inputs.
  • Receive authoritative state.
  • Find the matching simulation point.
  • Correct state.
  • Replay unacknowledged inputs.

07 — Remote Player Interpolation

Other players should normally be rendered from buffered snapshots with interpolation rather than jumping between network packets.

Snapshot A → Snapshot B
       ↓
     INTERPOLATE
       ↓
Smooth remote player

08 — Extrapolation

Use carefully. Extrapolation can help during packet gaps but can become visibly wrong during tackles and direction changes. Prefer conservative presentation over confident hallucination.

09 — Tick Rate

Define simulation and network tick rates explicitly. Do not let render FPS determine network gameplay timing.

Test under realistic load rather than assuming local LAN behaviour represents the final experience.

11 — Networked Ball

The ball is especially sensitive. Clients may predict local visual movement, but the authoritative ball state must come from the simulation.

Important state:

  • Position.
  • Velocity.
  • Angular state if used.
  • Ball gameplay state.
  • Last interaction.
  • Authoritative tick.

12 — Tackle Validation

Client: "I hit Player B"
          ↓
Server receives action
          ↓
Validate position/time/state
          ↓
Validate hitbox interaction
          ↓
Resolve impact
          ↓
Replicate result

Never trust a client-provided "hit confirmed" message.

13 — Lag Compensation

For short, high-value interactions, server-side rewind or historical state can be considered.

Use only where the gameplay benefit justifies the complexity. The goal is fair interaction, not perfect recreation of every historical frame.

14 — Ownership

Ownership should be explicit for networked entities. Avoid ambiguous ownership of the ball during contested interactions.

15 — Simultaneous Events

When multiple players interact with the ball or each other in the same tick, define deterministic arbitration.

18 — Anti-Cheat Principles

Never trust:

  • Client position.
  • Client speed.
  • Client kick power.
  • Client goal confirmation.
  • Client collision result.
  • Client cooldown completion.

Validate constraints server-side.

19 — Disconnect / Recovery

Define what happens when a player disconnects during:

  • Normal play.
  • Tackle.
  • Possession.
  • Goal sequence.
  • Match transition.

Never allow a disconnected entity to leave the match in a broken state.

This separation makes prediction, testing and reconciliation possible.

21 — Anti-Patterns

  • Client-authoritative score.
  • Client-authoritative goals.
  • Streaming raw transform every frame as the entire architecture.
  • Using network correction to hide a broken movement model.
  • Adding networking after the physics architecture is complete.
  • Trusting client hit detection for competitive actions.

23 — Automated Tests

  • Client prediction converges toward server state.
  • Reconciliation does not create visible repeated teleportation.
  • Server rejects impossible speed.
  • Server rejects impossible kick range.
  • Goal cannot be client-forged.
  • Ball cannot be client-teleported.
  • Simultaneous interactions resolve deterministically.

24 — Senior Developer Decision Rules

01. Responsiveness belongs on the client; truth belongs on the server.
02. Never sacrifice authority to hide latency.
03. Never sacrifice local responsiveness when prediction can solve the problem.
04. Network gameplay state must be explicit.
05. The ball deserves the same networking discipline as the player.
06. Test bad networks intentionally.
07. If an interaction cannot be explained under latency, redesign it before adding hacks.

25 — Definition of Done

  • Local movement feels immediate.
  • Remote players appear smooth.
  • Server remains authoritative.
  • Ball state is consistent.
  • Tackles are validated.
  • Goals are impossible to forge.
  • Reconciliation is rare and visually controlled.
  • Bad-network testing is part of QA.
FINAL PRINCIPLE
A multiplayer game is not finished when two computers can exchange positions. It is finished when players with different latency still believe they are playing the same game.
