Match Rules

The authoritative rules layer that turns movement, ball interaction, physics, actions and networking into one deterministic football match.

Design target: Players should always understand what the match expects, why a goal or reset happened, and what gameplay state comes next.

CORE PRINCIPLE
The Match Rules system decides what the match means. It does not move players, simulate physics or own presentation. It consumes authoritative gameplay events and produces explicit match commands/state transitions.

01 — Match State Is Independent

The existing architecture already separates global match state from player state. Keep that separation strict.

A player can be in RAGDOLL while the match is PLAYING. A goal can freeze the match while players remain in their current physical state for presentation.

02 — Match State Machine

StateAuthorityGameplay
BOOTMatchControllerInitialize rules and dependencies.
LOBBYMatchControllerPlayers connect/select/ready.
LOADINGMatchControllerLoad arena and spawn configuration.
COUNTDOWNMatchControllerFreeze active play; prepare kickoff.
PLAYINGMatchControllerNormal gameplay and scoring.
GOALMatchControllerLock scoring, record goal, present event.
RESETMatchControllerReset ball, players and kickoff configuration.
MATCH ENDMatchControllerStop active scoring and determine result.
RESULTSMatchControllerExpose final score/result.

03 — Match Authority

The server is authoritative for all match-critical outcomes.

GAMEPLAY EVENT
      ↓
SERVER MATCH RULES
      ↓
VALIDATE
      ↓
UPDATE MATCH STATE
      ↓
EMIT MATCH EVENT
      ↓
REPLICATE RESULT
  • Goal validation
  • Score
  • Match timer
  • Kickoff/reset
  • Match end
  • Victory condition
  • Critical boundary events

04 — Goal Resolution

A goal is not simply a trigger callback. Treat it as a deterministic gameplay event.

BALL / GOAL TRIGGER
        ↓
GOAL CANDIDATE
        ↓
VALIDATE MATCH STATE
        ↓
VALIDATE BALL STATE
        ↓
DETERMINE SCORING TEAM
        ↓
LOCK SCORING
        ↓
INCREMENT SCORE
        ↓
EMIT GOAL EVENT
        ↓
GOAL PRESENTATION
        ↓
RESET
Important: Presentation must never decide whether a goal happened. The authoritative match rules layer decides first; camera, audio, VFX and UI react afterward.

05 — Goal Lock

Once a goal is authoritatively resolved, prevent duplicate scoring while the match enters the GOAL state.

During GOALRule
ScoreCannot increment again.
Goal detectionIgnored or gated.
Normal scoring actionsDisabled for the reset phase.
PresentationAllowed.

        ↓

Reset must be deterministic. Do not rely on whatever physical state happened to remain after the goal.

07 — Boundaries & Ball Out

Boundary logic must be explicit and separated from generic world collision.

EventPossible rule layer response
Ball crosses touchlineStop/reset ball and start configured restart.
Ball crosses goal line outside goalRestart according to configured rule.
Player leaves legal arenaConstrain, respawn or recover according to arena rules.
Ball enters goal volumeRun goal resolution.

The exact restart types are deliberately data-driven so future modes can change them without rewriting the MatchController.

08 — Timer

The timer belongs to authoritative match state, not UI.

SERVER MATCH CLOCK
        ↓
MATCH TIME REMAINING
        ↓
HUD / PRESENTATION

Rendering a timer is presentation. Deciding whether the match has ended is match authority.

Rule: Never let client frame rate determine the official match clock.

09 — End Condition

Match end must be a single deterministic evaluation.

TIME / MODE END EVENT
        ↓
STOP SCORING
        ↓
EVALUATE RESULT
        ↓
WIN / LOSS / DRAW
        ↓
MATCH END
        ↓
RESULTS
ConditionResult
Team A score > Team BTeam A wins.
Team B score > Team ATeam B wins.
Equal scoreDraw, unless the mode defines another resolution.

10 — Overtime / Tiebreaker Hook

Do not hard-code overtime into the core match flow. Expose a rule policy.

REGULATION END
      ↓
RESULT?
 ├── YES → MATCH END
 └── NO  → OVERTIME POLICY
             ↓
        EXTRA PERIOD / GOLDEN GOAL / PENALTIES / DRAW

The core system should support these policies without assuming which one the final game mode uses.

14 — Anti-Patterns

  • Goal decided by client UI.
  • Score modified by player scripts.
  • Timer owned by HUD.
  • Physics callback directly changing score without validation.
  • Camera deciding match state.
  • Hard-coded rules inside individual actions.
  • Using arbitrary booleans instead of explicit match states.

15 — Definition of Done

  • Match state is explicit and authoritative.
  • Goal resolution is deterministic.
  • Duplicate goals are impossible.
  • Score exists only in match authority.
  • Timer cannot be forged by a client.
  • Reset produces a known deterministic state.
  • Match end is deterministic.
  • Mode-specific rules are data-driven.
  • Presentation reacts to semantic match events.
FINAL PRINCIPLE
The Match Rules system should be able to explain, at any instant, why the match is in its current state and what event is allowed to happen next.
