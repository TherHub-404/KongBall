## Technical Audit → Design Synthesis → Gameplay Optimization → 3D Integration → Implementation

You are working on an existing game project called KONGBALL.

This is NOT a greenfield project.

The game already exists, has already been developed, and already has a working multiplayer implementation. The game can already be played and tested in multiplayer. There are existing gameplay systems, code, scenes, assets, physics, networking and technical decisions.

This session is NOT intended to restart the project or rebuild everything from scratch.

Instead, this is a major consolidation and optimization session.

You are being given:
- the existing project
- a collection of HTML design and technical documents from the previous design phase
- existing and/or new 3D assets

Your job is to understand all of this together and turn it into a more coherent, fun, technically robust and visually consistent version of Kongball.

Behave like an experienced gameplay / technical developer joining an existing game project and performing a deep technical and gameplay audit before making significant changes.

Do not blindly follow the documents.
Do not blindly preserve the existing implementation.

Understand both.

Then make the best technical and gameplay decisions for Kongball.

# 01 — WHAT IS KONGBALL?

Kongball is a mobile-first arcade football game where monkeys play football.

Core format: 3v3.

The game should feel:
- arcade
- physical
- playful
- chaotic
- funny
- responsive
- readable
- easy to understand
- difficult to master
- highly replayable

The characters are stylized cartoon 3D monkeys with a toy-like physical quality.

They should NOT feel like realistic football players with monkey skins.

They should feel like:

PLAYFUL MONKEYS PLAYING CHAOTIC CARTOON FOOTBALL.

Physicality is a fundamental part of the game's identity.

Players should be able to:
- move
- jump
- kick the ball
- grab other players
- push other players
- collide
- get knocked back
- stumble
- potentially ragdoll
- recover
- score goals

The game should create moments where the player thinks:

"That was ridiculous."

and immediately wants to play again.

However:

CHAOS MUST NEVER DESTROY READABILITY OR CONTROL.

The game should feel chaotic visually and physically while remaining understandable from a gameplay perspective.

# 02 — WHY KONGBALL IS DESIGNED THIS WAY

Before implementing anything, understand WHY Kongball is designed this way.

The goal is NOT to create a realistic football simulator.

The goal is to create a highly readable, physical, funny and replayable arcade football game.

The game should have:

VERY SIMPLE INPUT
+
RICH INTERACTION
+
PHYSICAL GAME FEEL
+
STRONG CHARACTER IDENTITY
+
SHORT LEARNING CURVE
+
HIGH SKILL CEILING

### Why simple controls?

Kongball is mobile-first.

The player should mainly think:

MOVE
JUMP
ACTION

The complexity should come from:
- positioning
- timing
- physics
- opponents
- ball trajectory
- spatial awareness
- teamwork
- risk/reward

NOT from having many buttons.

### Why contextual ACTION?

ACTION changes depending on the player's relationship with the ball.

WITH BALL:
ACTION = KICK

WITHOUT BALL:
ACTION = GRAB / PUSH

One button represents:

"DO THE MOST RELEVANT INTERACTION RIGHT NOW."

### Why physical gameplay?

Physicality is one of Kongball's main differentiators.

The ball should feel physical.
Players should feel physical.
Collisions should feel physical.
Kick, grab, push, knockback and ragdoll should create memorable moments.

However:

PHYSICAL DOES NOT MEAN UNCONTROLLED.

Physics should support gameplay rather than replace gameplay design.

### Why monkeys?

The monkey characters are not just a visual skin.

Their identity should influence:
- movement
- animation
- reactions
- body language
- comedy
- physicality
- game feel

The player should feel that they are controlling a playful monkey, not a footballer with a monkey model.

### Why cartoon physics?

Exaggerated physical reactions make the game more readable and entertaining.

A kick should feel like a kick.
A grab should feel impactful.
A push should communicate force.
A collision should create a clear reaction.
A ragdoll should be funny.

### Why separate gameplay from visuals?

Gameplay must remain reliable.

The visual model can be complex.
The gameplay collider can be simple.
The animation can be exaggerated.
The gameplay state must remain authoritative.

### Why multiplayer-first thinking?

Kongball is already multiplayer.

Every gameplay-critical system must remain compatible with the existing multiplayer architecture.

Do not create local-only gameplay shortcuts that break multiplayer consistency.

### Why is documentation not automatically the source of truth?

The HTML documents represent previous design thinking.

They contain valuable decisions, but may also contain:
- experiments
- obsolete ideas
- duplicate solutions
- assumptions
- tuning values
- contradictions

The source of truth should ultimately become:

GAME VISION
+
ACTUAL PROJECT
+
VALIDATED GAMEPLAY
+
MASTER DEVELOPMENT DOCUMENT

### Why audit before implementation?

Because the game already exists.

Blindly implementing every document could create:
- duplicate systems
- conflicting architectures
- unnecessary refactors
- technical debt
- broken multiplayer
- unnecessary complexity

Therefore:

UNDERSTAND FIRST.
DECIDE SECOND.
IMPLEMENT THIRD.
TEST FOURTH.
DOCUMENT FIFTH.

### Why challenge the documentation?

The objective is not to prove that previous design decisions were correct.

The objective is to make Kongball better.

If you find a simpler, more robust or more fun solution:
PROPOSE IT.

If a previous decision is bad:
EXPLAIN WHY.

If two documents conflict:
SURFACE THE CONFLICT.

If something is unnecessary:
SUGGEST REMOVING IT.

Never silently change a fundamental decision.

### Why tunable systems?

Game feel cannot be fully designed on paper.

Numbers such as acceleration, jump velocity, gravity, air control, kick power, kick timing, grab range and knockback should generally be treated as starting hypotheses unless explicitly marked otherwise.

They must be easy to tune through playtesting.

# 03 — CORE MOBILE CONTROLS

The core mobile control scheme is intentionally extremely simple.

There is a movement control on the left.

There are two gameplay buttons on the right:

1. ACTION
2. JUMP

ACTION is contextual.

If the player HAS the ball:

ACTION = KICK

If the player DOES NOT have the ball:

ACTION = GRAB / PUSH

JUMP:

JUMP = JUMP

Do not introduce unnecessary additional buttons unless there is an extremely strong gameplay reason.

The fundamental interaction is:

MOVE + ACTION + JUMP

Everything else should emerge from these simple inputs.

# 15 — ACTION SYSTEM

ACTION is contextual.

WITH BALL:
ACTION → KICK

WITHOUT BALL:
ACTION → GRAB / PUSH

Implement this as a contextual action system rather than two unrelated button systems.

The input communicates:

ACTION INTENT

The game then determines:
- current player state
- ball state
- target availability
- distance
- angle
- action availability
- action priority

and resolves the correct action.

---

# 16 — KICK

Kick should be responsive and satisfying.

It should have:
- input
- intent
- validation
- windup
- active contact window
- ball resolution
- launch
- follow-through
- recovery

Animation communicates the kick.

Gameplay determines when contact is valid.

Animation must NOT become the authoritative source of ball collision.

The ball remains an independent gameplay object.

---

# 17 — JUMP + KICK

This interaction is especially important.

The player must be able to jump and potentially kick while airborne.

However:

JUMP DOES NOT AUTOMATICALLY MEAN AIR KICK.

The player must be in a valid ball interaction context.

Conceptually:

JUMP
↓
AIRBORNE
↓
ACTION
↓
IS BALL IN VALID AIR KICK ZONE?
↓
YES → AIR KICK
NO → NO VALID KICK

The air kick should reuse the same fundamental ball interaction architecture as the ground kick.

Do not create an entirely separate ball physics system for air kicks.

---

# 18 — GRAB / PUSH

Without the ball, ACTION becomes player interaction.

The player can:
- grab
- hold
- push
- release
- potentially throw / knock back if supported by the existing design

Use explicit gameplay queries / hitboxes.

Do not rely on random Rigidbody collisions to determine whether a grab succeeded.

Target selection should consider:
- range
- angle
- state
- availability
- priority

The result must be deterministic and readable.
