Gameplay State & Action System

The control layer that coordinates movement, physics, ball interaction and character reactions into one coherent gameplay model.

Design target: No system should fight another system. At any instant, the game must know what the player is allowed to do, what has authority, and what happens next.

CORE PRINCIPLE
The player is not a collection of independent scripts. The player is a stateful gameplay entity with explicit authority, transitions and actions.

01 — Why a State System Exists

Without explicit state ownership, a typical prototype becomes:

Movement script → moves
Kick script → moves
Tackle script → moves
Ragdoll script → moves
Animation event → moves
Network correction → moves

This creates race conditions and impossible combinations. The state/action system decides which system is allowed to control gameplay.

Do not create a giant enum that tries to represent every combination. Separate high-level state from orthogonal flags/data where appropriate.

03 — State Authority

At any moment there must be one clear answer to:

  • Who controls horizontal movement?
  • Who controls vertical movement?
  • Can input be accepted?
  • Can the player start another action?
  • Can the player be interrupted?
  • Is the player invulnerable?

04 — State Priority

NORMAL LOCOMOTION
       ↓
ACTION
       ↓
IMPACT
       ↓
KNOCKBACK / RAGDOLL
       ↓
RECOVERY

Higher-priority states can temporarily override lower-priority states.

Do not use arbitrary booleans as hidden priority. A dozen flags such as isKicking, isStunned, isFalling and canMove eventually create contradictory states.

05 — Actions vs States

A state describes the current gameplay condition. An action is something the player attempts to do.

ActionPossible result
KickKick state → ball launch → recovery
TackleTackle → hit / miss → recovery
JumpAirborne state
MoveLocomotion update

07 — Action Cancellation

Cancellation must be explicit. Examples:

  • Can sprint cancel into tackle?
  • Can kick cancel into jump?
  • Can a tackle be interrupted by knockback?
  • Can an impact interrupt a kick before its active frame?

Define cancellation windows instead of allowing arbitrary script overrides.

08 — Input Buffering

For short actions, accept input slightly before the character becomes available.

Examples: jump near landing, kick immediately after recovery, tackle after sprint.

Buffer duration must be short and configurable. Buffering should make controls forgiving, not queue a whole combo system accidentally.

09 — Interruptions

Every action should declare whether it can be interrupted by:

  • Player input.
  • Environment collision.
  • Tackle.
  • Knockback.
  • Ragdoll.
  • Match events.

10 — Gameplay Commands

Prefer commands/events between systems instead of direct cross-system mutation.

TackleHit
 ↓
ImpactResolver
 ↓
ApplyKnockbackCommand
 ↓
PlayerState
 ↓
MovementMotor

This keeps the architecture testable and prevents circular dependencies.

11 — Action Data

Actions should be data-driven where possible:

  • Windup.
  • Active window.
  • Recovery.
  • Cooldown.
  • Hitbox.
  • Allowed states.
  • Interrupt rules.
  • Impact tier.
  • Animation/VFX/SFX references.

13 — Global Authority

Some events override player state entirely:

  • Goal.
  • Match end.
  • Respawn.
  • Round reset.
  • Pause if supported.

14 — Deterministic Transitions

For the same state + action + event, the transition should be predictable. Avoid hidden dependencies on frame timing.

15 — Animation Integration

State changes emit semantic animation parameters. Animation does not become the owner of gameplay state.

Gameplay State
 ↓
Animation State
 ↓
Visual Motion

16 — Debug State Inspector

Build a live inspector showing:

  • Current state.
  • Previous state.
  • Current action.
  • Action phase.
  • Time remaining.
  • Allowed actions.
  • Interruptible?
  • Authority source.

17 — Automated Tests

  • Illegal actions are rejected.
  • Higher-priority impacts override locomotion correctly.
  • Every action exits its state.
  • Every ragdoll has recovery.
  • Input buffering does not execute stale actions.
  • Match state cannot be modified by local player scripts.
  • Same event sequence produces the same state transitions.

18 — Anti-Patterns

  • Dozens of interacting booleans defining hidden state.
  • Directly setting another system's transform from an action script.
  • Animation events deciding whether a tackle succeeded.
  • Cooldown logic scattered across multiple components.
  • Actions with no recovery path.
  • State transitions that depend on random frame timing.

19 — Senior Developer Decision Rules

01. Every gameplay state must have an owner.
02. Every action must have a lifecycle.
03. Every interruption must be explicit.
04. Higher-priority gameplay events override lower-priority locomotion.
05. Never solve state conflicts with another boolean.
06. Gameplay state is authoritative; animation is presentation.
07. If Claude cannot draw the state transition, the state system is probably too implicit.

20 — Definition of Done

  • Every action has clear phases and transitions.
  • No scripts fight for movement authority.
  • Interruptions are deterministic.
  • State transitions are debug-visible.
  • Actions are data-driven where useful.
  • Player state and match state are cleanly separated.
  • The system can support new actions without rewriting existing actions.
FINAL PRINCIPLE
A great state system makes complex gameplay feel simple because the player never sees the machinery. They simply press a button and the game responds correctly.
