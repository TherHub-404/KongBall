Gameplay Engineering Bible · KB 08

Football Actions

The authoritative action catalogue for movement-to-ball interactions: readable, responsive and forgiving enough for arcade play without removing player skill.

Design target: Every football action must have a clear intention, a predictable active window, a defined interaction result and a controlled recovery.

CORE PRINCIPLE
An action is not an animation and it is not a physics impulse. It is a gameplay command that passes through validation, timing, interaction resolution and recovery.

01 — Action Architecture

INPUT
  ↓
PLAYER INTENT
  ↓
CAN ACTION?
  ↓
START ACTION
  ↓
WINDUP
  ↓
ACTIVE WINDOW
  ↓
RESOLUTION
  ↓
RECOVERY
  ↓
RETURN TO VALID STATE

This follows the existing state/action architecture. Actions must not directly fight movement, physics, networking or animation systems.

Every action should expose the same conceptual data.

ActionData
├── ActionId
├── AllowedStates
├── WindupDuration
├── ActiveDuration
├── RecoveryDuration
├── Cooldown
├── InputBuffer
├── CancelRules
├── Hitbox / Query
├── InteractionType
├── Power
├── Assist
├── ImpactTier

Centralizing this data makes actions tunable without scattering constants across gameplay scripts.

    ↓

05 — Kick Contact Quality

QualityGameplay result
PoorWeak or awkward contact.
NormalExpected launch.
CleanStrong and accurate launch.
PerfectOptional advanced mechanic; only use if it adds meaningful skill.
Assist rule: aim assist and magnetism may increase the probability of clean contact, but must not guarantee a successful outcome.

06 — Pass

Pass is a kick variant with a different intent profile rather than a completely separate physics system.

PASS
 ↓
SELECT INTENDED DIRECTION / TARGET
 ↓
VALIDATE BALL CONTACT
 ↓
BOUNDED AIM ASSIST
 ↓
APPLY PASS LAUNCH MODEL
 ↓
BALL SIMULATION

The ball remains authoritative and physical after launch. The pass system chooses the launch command; it does not own the ball afterward.

 ↓
AIM CONE
 ↓
POWER

Shot power, vertical lift, spin and maximum speed should remain data-driven and centralized.

08 — Dribble / Controlled Touch

Controlled touch should not make the ball a child of the player transform. The ball remains a gameplay object with physical state.

PLAYER INTENT
    ↓
CONTROL ZONE
    ↓
VALIDATE BALL
    ↓
CALCULATE TOUCH TARGET
    ↓
BOUNDED CORRECTION
    ↓
APPLY TOUCH
    ↓
BALL REMAINS PHYSICAL

The existing ball architecture explicitly requires this separation.

09 — Header

Header is an airborne interaction using a dedicated header zone.

HEADER INPUT
    ↓
CHECK AIRBORNE BALL
    ↓
CHECK HEADER ZONE
    ↓
RESOLVE CONTACT
    ↓

    ↓

    ↓

Header should use the same ball command pipeline as kicks where possible, with different contact geometry and tuning.

VALIDATE

12 — Jump

Jump is primarily a locomotion action, but it changes which football interactions are valid.

StateAllowed interactions
GroundedKick, tackle, jump, normal control.
AirborneHeader where valid; limited ground actions.
ImpactDefined by interruption rules.

13 — Action Cancellation

Cancellation must be authored per action.

ActionPossible cancellation
SprintTackle / jump where permitted.
KickMay be interrupted before active contact.
TackleUsually committed after active phase begins.
JumpTransitions into airborne state rather than arbitrary cancellation.

Do not implement cancellation as random script overrides.

14 — Input Buffering

Short buffers make the controls forgiving without creating a combo queue.

INPUT EARLY
    ↓
SHORT BUFFER
    ↓
ACTION BECOMES AVAILABLE
    ↓
EXECUTE

Useful examples include kick immediately after recovery, jump near landing and tackle after sprint.

15 — Action Priority

NORMAL
 ↓
ACTION
 ↓
IMPACT
 ↓
KNOCKBACK / RAGDOLL
 ↓
RECOVERY

Higher-priority gameplay states may interrupt lower-priority actions according to explicit rules.

16 — Ball Interaction Priority

When multiple interactions are possible in the same simulation window, resolve them deterministically.

COLLECT CANDIDATES
      ↓
VALIDATE STATES
      ↓
SCORE / PRIORITIZE
      ↓
RESOLVE ONE AUTHORITATIVE RESULT
      ↓
APPLY BALL COMMAND
      ↓
EMIT EVENT

Candidate scoring may consider distance, angle, action priority, contact quality and simulation order.

17 — Multiplayer Contract

Clients request actions. The authoritative simulation validates them.

CLIENT INPUT
    ↓
LOCAL PREDICTION
    ↓
ACTION COMMAND
    ↓
SERVER VALIDATION
    ↓
AUTHORITATIVE RESOLUTION
    ↓
REPLICATION
    ↓
PRESENTATION
Never trust: client-confirmed tackles, client-confirmed goals, client-provided ball positions or impossible action timing.

18 — Presentation Contract

Actions emit semantic events. Animation, VFX, SFX, camera and haptics react to those events.

KickResolved
 ├── Animation
 ├── VFX
 ├── SFX
 ├── Camera
 └── Haptics

This keeps gameplay authority separate from presentation while maintaining one coherent response.

19 — Anti-Patterns

  • Using animation events as authoritative gameplay logic.
  • Letting the ball become a child of the player.
  • Putting kick/tackle physics directly inside the movement controller.
  • Letting collision callbacks decide every interaction.
  • Guaranteeing success with aim assist.
  • Allowing client-side action results to become authoritative.
  • Creating a separate physics implementation for every football action.

20 — Definition of Done

  • Every player action has explicit timing.
  • Every action declares allowed states and interruption rules.
  • Ball actions use the shared interaction pipeline.
  • Assist is bounded and skill-preserving.
  • Tackles use authored hitbox/query logic.
  • Ball results are authoritative.
  • Actions are data-driven.
  • Presentation reacts to semantic events.
  • Actions remain predictable under multiplayer latency.
FINAL PRINCIPLE
The player should feel that their intention caused the action, while the game remains free to resolve that intention through controlled timing, assistance, physics and authoritative rules.
